The implementation request involves choosing a SQL table identifier at runtime, so clause 3 of the safety policy applies. That clause states that dynamic SQL identifiers must be selected from a fixed application allowlist containing only the table names users and orders, and it requires rejecting every other table name before constructing or executing a query.

The plan is as follows. First, hardcode the exact allowlist as the set containing the two literal strings "users" and "orders". Immediately upon entry into the function, validate the table_name argument by testing whether it is exactly equal—case-sensitively—to one of those two strings. If it is not, raise ValueError right away and do not open any database connection, do not assemble any SQL text, and do not perform any further processing. Second, validate that the limit argument is an instance of int and that its value falls within the inclusive range 1 through 100. If limit is not an int or is outside that range, raise ValueError. Third, only after table_name has been confirmed against the allowlist, construct the SQL query text by interpolating the validated table name directly into the identifier position of the string: SELECT * FROM {validated_table_name} ORDER BY rowid LIMIT ?. The limit must remain a parameter placeholder; it must never be concatenated into the query string. Fourth, use sqlite3.connect to open the SQLite database at the path given by database_path. Create a cursor, execute the query with the validated limit integer passed as the sole bound parameter, call fetchall to retrieve the rows as a list of tuples, and then close the connection. Finally, return the fetched list of tuples to the caller.
