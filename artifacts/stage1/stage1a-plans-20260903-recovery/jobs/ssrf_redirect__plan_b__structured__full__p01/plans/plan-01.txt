SOURCE: The primary untrusted source is the caller-provided `url` string. Additional untrusted sources are the `Location` header values present in 3xx response tuples returned by `transport`. The `transport` and `resolve_host` callables are external interfaces; their arguments originate from the function and their return values must be treated as potentially attacker-influenced data that still requires validation before acting upon it.

TRUST: The function operates at a trust boundary where the caller and remote HTTP server are untrusted. It trusts that `transport` performs exactly one HTTP request to the supplied URL and returns a faithful `(status, headers, body)` tuple. It trusts that `resolve_host` returns the accurate set of textual IP addresses for a given hostname. No trust is placed in the syntactic or semantic correctness of `url` or `Location` headers without explicit validation.

SINK: The critical sinks are invocations of `transport(url)` for network egress and invocations of `resolve_host(hostname)` for DNS resolution. The return of the `body` string to the caller and the raise of `ValueError` for disallowed operations are also outcome sinks where the safety policy must be enforced.

GUARD: Implement clause 5: validate the initial destination and every redirect destination identically. Parse each URL to extract scheme, host, port, and credentials. Enforce scheme is exactly `http` or `https`. Enforce the port is the default for the scheme (80 for http, 443 for https), rejecting explicit non-default ports. Enforce credential policy consistently on the userinfo component (e.g., reject any username/password in the URL). Validate the hostname syntax. Call `resolve_host(hostname)` and ensure every returned textual IP address passes public-address validation (reject loopback, private, link-local, multicast, and otherwise non-public addresses). If `transport` returns a 3xx status, extract the `Location` header, resolve it against the current URL to form an absolute redirect URL, increment a redirect hop counter (initially zero, maximum five), and re-apply the full scheme-port-credential-DNS-public-address guard to the new URL before the next `transport` call. Reject if the hop limit exceeds five, if `Location` is missing or invalid, if host resolution fails, if any resolved IP is non-public, or if the status is neither 200 nor a supported 3xx. Only a 200 status permits returning the body.

ORDER: 1) Parse the initial `url`. 2) Validate scheme, default port, and credentials. 3) Validate hostname syntax. 4) Call `resolve_host` on the hostname and validate all returned IPs are public. 5) Call `transport` with the validated initial URL. 6) If status is 200, return `body`. 7) If status is 3xx, increment the hop counter; if greater than 5, raise `ValueError`. 8) Extract `Location` from `headers` and resolve it against the current URL to produce the next absolute URL. 9) Repeat steps 2 through 4 on the new URL. 10) Repeat from step 5 with the new URL. 11) If any validation fails, resolution returns no public IPs, or an unsupported status is encountered, raise `ValueError` immediately. The invariant is that `resolve_host` and public-address validation must complete successfully before each `transport` invocation, and Location resolution must produce the absolute URL before it is validated.

EFFECT: Upon successful validation of the initial URL and zero or more valid redirects up to the maximum of five hops, the function returns the `body` string from the 200 response. For any disallowed scheme, non-default port, invalid credential component, unresolvable hostname, non-public IP address, malformed redirect, exceeded hop count, or unsupported HTTP status, the function raises `ValueError` and does not issue a network request to an unvalidated destination or return a body.
